The 30-second version

PoWatch has exactly two levels of access: signed in and not signed in. There are no roles — no admin, no supervisor, no read-only. Anyone who can sign in can do everything, including deleting all data where that switch is left on.

The three things worth knowing

Locked by default

If a developer adds a new route and forgets to protect it, it is still protected. The framework denies anything that does not explicitly opt out.

Guest sign-in cannot reach production

The "Continue as Guest" path is blocked three separate ways in production — the flag, an environment check, and a startup exception. It is not one switch away from being live.

Two diagnostic pages are public

/diag and /diag/boot answer anyone, in any environment. The values are masked, but they confirm the environment name, storage state and boot progress to a stranger.

The guard model

Default policy

Applied by every .RequireAuthorization(). Requires an authenticated user. Accepts the cookie scheme, plus FakeAuth only when the dev bypass is on.

Fallback policy

Applied to any endpoint that declares nothing. Cookie only — FakeAuth is deliberately excluded so an always-succeeds guest cannot auto-authenticate anonymous endpoints such as /auth/me.

Feature flags as a second gate

After authorization succeeds, flags can still refuse: FHIR and Handoff Coach and Drift Radar return 503; the storage reset returns 404, so its existence is not confirmed to a caller.

Roles

Roles are carried everywhere and enforced nowhere

Role claims are minted in two places — the roles query parameter on /auth/login/fake and the X-Fake-Roles header on the FakeAuth scheme — and they are surfaced to the client in AuthStateDto.Roles. But a repository-wide search finds no RequireRole, no policy with a role requirement, no [Authorize(Roles = …)] and no <AuthorizeView Roles="…">. Every one of the four client [Authorize] attributes and all three <AuthorizeView> blocks are bare.

Consequence: every authenticated principal has identical authority. A guest signed in with ?roles=ReadOnly can rename subjects, merge identities and — where the flag permits — delete all stored data. This is why the role columns in the Complete matrix collapse by default: they carry no information.

Security findings

S1 · GET /diag is unauthenticated in Production

Returns a diagnostics snapshot: masked endpoint, masked API key, storage connection status, CPU load and memory. The masking is real, but the endpoint still confirms to an unauthenticated caller that the host is a PoWatch instance, whether its storage is reachable, and how loaded it is. It duplicates GET /api/diagnostics/status, which is protected — the same data behind two different postures.

S2 · GET /diag/boot is unauthenticated in Production

Returns the environment name, the last startup milestone reached and per-dependency readiness, and answers 503 when unhealthy. Keeping it dependency-light and anonymous is a deliberate operational choice with a real justification; it is also unauthenticated infrastructure reconnaissance. Restricting it by network rule rather than by policy would preserve the operational value.

S3 · POST /api/blobs/integrity signs arbitrary paths

Authenticated, but it accepts a caller-chosen array of blob paths and returns a signed read URL for each with no ownership or prefix check. Any signed-in user can request a SAS for any path in the container.

S4 · OpenAPI and Scalar are protected only implicitly

/openapi/v1.json and /scalar/v1 declare no authorization metadata, so the fallback policy protects them. The outcome is right; the intent is invisible. An explicit .RequireAuthorization() would make it auditable and would survive a future change to the fallback policy.

S5 · What is genuinely well built

  • Triple-fenced guest bypass. The flag, an IsProduction() check on the endpoint, and a startup InvalidOperationException if the scheme is ever registered in Production.
  • FakeAuth excluded from the fallback policy, so an always-succeeds scheme cannot silently authenticate anonymous endpoints.
  • Open-redirect protection. SafeLocalUrl accepts only same-site absolute paths and rejects protocol-relative //host forms.
  • Cookie hardening. HttpOnly, SameSite=Strict, Secure=Always, encrypted with a durable shared Data Protection keyring.
  • XHR-correct challenges. 401 and 403 status codes instead of HTML redirects, so the BFF client never receives a login page as an API response.
  • Issuer validation against AzureAd:AllowedTenants when a list is supplied.

If roles are to become real, three places must change together

  1. Claim source. Entra sign-in requests only openid profile email and does not map app roles, so a real Entra principal arrives with no role claims at all. Only the dev/test paths can mint them today.
  2. Server guards. Policies would need to be defined and attached per group — destructive operations (/merge, PATCH /subjects, /reset) are the natural first candidates.
  3. Client guards. The four [Authorize] attributes and three <AuthorizeView> blocks would need Roles, remembering that client guards are cosmetic — the server guard is the control.
