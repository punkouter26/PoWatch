30-second overview

PoWatch is a mobile-first room-observation system. The browser watches the room using a small on-device vision model, posts one sentence per cycle to the same-origin API, and the API stores the event, classifies it, and surfaces it back as a live timeline, a daily chapter, an optional AI handoff brief, and a FHIR feed. One deployable, one origin, one cookie.

Layering, stated precisely

Domain depends on nothing. Application depends on Domain and its own contracts. Infrastructure implements those contracts. The API host composes them. Every outbound dependency sits behind an interface with an in-memory alternative, which is why the app boots without Azure.

Plain-English narrative walk-through

Eight step cards. Each card pairs a visual element with the consequences in the running code, so the picture and the explanation never drift apart.

[ caregiver kisses the wall display ]
Step 1 · caregiver

Caregiver presses Start

ObserverHub.razor.cs re-reads /api/observer/state to confirm the operator kill-switch is not set, then starts the camera preview and asks the inference worker to load the selected SmolVLM model. The loop runs in a Web Worker so the UI thread stays free.

[ loop · every 10 s ]
Step 2 · browser

Frame-diff, then infer

The bridge draws the latest frame to a canvas and compares it with the previous one. An unchanged frame ends the cycle — no model run, no network request. Otherwise the worker generates one short sentence, with up to four fallback attempts stepping device and precision on an empty reply.

[ same-origin · HttpOnly cookie ]
Step 3 · transport

Payload crosses the BFF boundary

The client attaches no token. The session is an encrypted HttpOnly cookie the browser sends automatically. A per-app-load X-Session-ID and an X-Correlation-ID thread the request through the server's logs.

[ pipeline · 9 stages ]
Step 4 · middleware

Pipeline runs in order

Exception handler → HTTPS redirect (non-Dev) → rate limiter → correlation id → authentication → authorization. A missing or expired cookie returns 401 — never an HTML redirect — so the client shows "Reconnecting" instead of rendering a login page inside the dashboard.

[ service · 4 gates ]
Step 5 · orchestrator

ObservationService decides

Four gates run in order: the ObservationLoopEnabled flag, the single-flight processing gate, the telemetry sanitizer, and the subject resolution. Significance and outlier status are decided here, never by the caller. The verdict is echoed back so the client stops second-guessing it.

[ tables · Polly · 3 retries ]
Step 6 · providers

The row is written

AzureObservationRepository.AddAsync with the row key derived from the stable event id (idempotent on retry, 409 treated as success). AzureSubjectRepository.UpdateLastActivityAsync merges only the activity columns, so a concurrent rename or identity merge is not clobbered. Both calls sit behind a Polly retry for transient faults.

[ 30-min SAS · direct PUT ]
Step 7 · evidence

Significant frames go straight to blob storage

The API mints a 30-minute SAS and the browser uploads the JPEG directly. The image never passes through the API, which is why a brief upstream stall does not block the dashboard. The observation row carries the ImageReference so the timeline can show it.

[ banner · cue · overlay ]
Step 8 · response

The caregiver sees the result

An outlier raises a full-screen takeover with the captured frame. A significant event raises a Watch banner. A dropped cycle renders "Dropped by API" with no follow-up queries. Acknowledging an alert explicitly evicts the HybridCache live-status key so the pressed button visibly does something.

// PoWatch.Domain.Models
public readonly record struct SubjectId(string Value)
{
    public static readonly SubjectId Empty = new(string.Empty);
    public static SubjectId From(string raw) => new(raw?.Trim() ?? string.Empty);
    public bool IsEmpty => string.IsNullOrWhiteSpace(Value);
    public override string ToString() => Value;
}

public readonly record struct ObservationEventId(Guid Value)
{
    public static readonly ObservationEventId Empty = new(Guid.Empty);
    public static ObservationEventId New() => new(Guid.NewGuid());
    public static ObservationEventId From(Guid id) => new(id);
    public bool IsEmpty => Value == Guid.Empty;
}

Gaps surfaced by this dashboard

What the system does not currently measure, enforce or surface. Each item is a known structural choice; calling them out here keeps the next planning round honest.

No AiPricing configuration in the repo

Per-token input, output and cached-input prices for gpt-5.4-nano are absent. Combined with the fact that the Azure OpenAI response's usage object is never deserialized, projected monthly cost cannot be derived and after-the-fact reconciliation cannot be performed.

Rate limiter does not enforce anything

AddSlidingWindowLimiter("ApiPerIpPolicy", …) registers a named policy and UseRateLimiter() runs — but no endpoint calls .RequireRateLimiting and no GlobalLimiter is set. The policy is also unpartitioned by IP despite its name; attaching it as written would create one global 60/min window.

TTFT is unmeasured on both AI services

Neither path streams, so the first-token event is not observable. The browser worker awaits a single generate(); the server POST reads the whole body. Adding TTFT requires switching to a streaming API on at least one path.

Four Roles columns exist but no role is ever checked

Roles are minted on the dev/test paths and surfaced in AuthStateDto, but no RequireRole, no policy with role requirement, no [Authorize(Roles=…)] and no <AuthorizeView Roles="…"> exists. Until that is fixed, every authenticated principal has identical authority.

Browser weight fetches are not pinned to a revision

transformers.js is self-hosted and pinned by folder name; the model weights are fetched from the Hugging Face Hub with no revision parameter. An upstream repository change silently alters what the browser executes.
